# RTL 阶段 1 验证报告

日期：2026-09-15。基线：`Design_Spec_V1.2.md`、`RTL_Coding_Style.md` v1.7。

结论：阶段 1 的 6 个 RTL 模块、2 个公共 include 文件通过严格 Verilog-2001 编译和本阶段回归。共 14 项仿真配置通过，另有 8 组非法容量/指针参数按预期在 elaboration 阶段被拒绝。

工具：Icarus Verilog 13.0 stable / VVP，Windows x64；编译选项 `-g2001 -Wall`，合法配置编译结果无 warning。

```powershell
py -3 -B scripts/run_stage1.py
```

完整日志和精确源文件 SHA256 位于 `build/stage1/results.json` 及同目录日志。工具包使用 [MSYS2 Icarus Verilog 发布包](https://packages.msys2.org/packages/mingw-w64-x86_64-iverilog)，版本、来源和包校验值锁定在 `scripts/iverilog_msys2.lock.json`。

### 2.1 RAM 关键检查

- 读地址在时钟边沿之间变化时，输出保持上一次同步读的结果。
- 读数据在读请求沿之后立即可用，没有增加第二个输出寄存器周期。
- 同址物理写和读返回新写值，覆盖 NEXT 延迟修补与读重叠的 RAM 接口条件。
- 将同址读写时的原始宏输出强制为 X，外部读结果仍由旁路正确提供。
- 新提交优先于 pending，pending 优先于物理写；不匹配的地址不能转发；零值可转发。
- 读请求后撤销源 overlay 并改变其 data，已捕获的读结果仍保持正确；下一次 raw read 不继承过时的 bypass 命中。
- 1RW 同拍读写冲突被指示并拒绝，两种访问都没有生效；之后回读确认原内容保留。
- 复位清 read_valid、抑制读写使能，RAM 本体内容不依赖异步清零。

这里验证的是 RAM 接口的 RAW 条件与旁路寿命。完整的 A→B→C 链表、插入 D 和紧接的 extract 事务测试将在顶层阶段执行。

### 2.2 容量与初始化

| PTR_WIDTH / MEM_DEPTH | ADDR_WIDTH | COUNT_WIDTH（测试中的 RC 字宽） | 初始化写沿数 | guard / 首个正常读沿 |
| :--- | :--- | :--- | :--- | :--- |
| 4 / 16 | 4 | 5 | 8192 | R8192 / R8193 |
| 5 / 16 | 4 | 5 | 8192 | R8192 / R8193 |
| 10 / 1024 | 10 | 11 | 8192 | R8192 / R8193 |
| 11 / 1024 | 10 | 11 | 8192 | R8192 / R8193 |
| 11 / 2048 | 11 | 12 | 8192 | R8192 / R8193 |
| 12 / 4096 | 12 | 13 | 8192 | R8192 / R8193 |
| 16 / 65536 | 16 | 17 | 65536 | R65536 / R65537 |

每组测试先在扫描期间复位，再执行完整初始化，随后回读 TT/RC 全 8192 项、L3 全 512 项、FREE 全 MEM_DEPTH 项，并检查全部 L1/L2 位为 0。FREE[i]=i，因此默认地址 0 和 1023 均被验证。最后检查运行中复位重新从地址 0 开始。

非法组合为 3/16、4/32、9/1024、10/2048、10/1000、10/8、17/1024、16/131072。拒绝机制是常量 generate 中仅在非法配置激活的未定义错误模块，避免依赖 SystemVerilog assertion 或 `$fatal`。后续综合流程必须将该类未解析实例视为错误，不允许当作合法黑盒继续。

## 3. 当前限制与下一阶段

当前没有完整 `wfq_tag_sort_engine` 顶层，尚未验证系统级排序、FCFS、epoch 窗口、FREE 分配回收、容量计数、响应背压、全局原子故障处理和 I=5/6 的事务排程。参数测试验证当前模块的容量配置与初始化，没有代替全引擎参数矩阵或故障注入。

风格脚本是机械规则的子集检查；复位拓扑、逻辑分区、存储宏推断和时序路径仍需人工/专用工具检查。当前 L1/L2 源码仅声明 544 bit 状态、RAM 每个实例仅一个数组，但尚无综合资源报告。异步复位同步器的物理约束、具体 SRAM/BRAM 宏映射以及工作频率由后续实现流程验证。

下一阶段按 `RTL_Implementation_Plan.md` 实现 Trie 搜索、TT/RC 管理和精确 marker 更新，并分别验证 FAST5 / PIPE6 排程。
