# wfq_tag_sort_engine 第三阶段 RTL 验证报告

日期：2026-09-16。基线：`Design_Spec_V1.2.md`；风格：`RTL_Coding_Style.md` v1.7。语言：Verilog-2001。

## 1. 交付与结论

第三阶段完成 FAST5 准入与资源控制：FREE 栈、容量预留、两代 epoch 窗口、RR 仲裁、保守响应信用、两项响应 FIFO，以及资源域的统一提交门控和首次故障锁存。新增五个实际功能模块，均列入 `rtl/files.f`：

| 模块 | 验证关注点 |
| :--- | :--- |
| `wfq_admission_ctrl` | 首次冲突优先出队、实际接受后换优先权、最小五拍间隔、无请求时不丢发射机会 |
| `wfq_free_slot_stack` | 单份 1R1W RAM、E1 分配返回、满容量计数、槽位 0 可用、分配预留、索引检查后缩窄 |
| `wfq_epoch_ctrl` | 两代完整身份及计数、65535→0、第三代背压、旧代清空推进、空队列任意重建 |
| `wfq_response_fifo` | 两项完整 payload、预留信用、E1 沿后有效、最早 E2 消费、同沿 push/pop、故障后消费 |
| `wfq_resource_ctrl` | 沿前错误取最小编码、插入 E4/出队 E1、统一资源门控、归属检查、响应生命周期独立 |

**完整第三阶段回归通过：14 项仿真、6 项配置拒绝检查，合法配置无编译 warning。** 默认 10/1024 的两组集成测试分别完成 7,698 和 7,842 次已接受并提交的操作，响应全部对拍并排空。

这是资源子系统的 RTL 结果。实际链表、DATA/NEXT、head cache、pending 和完整顶层仍未实现，不能据此宣称完整引擎已达到 `f_clk/5` 或某个 MHz。

## 2. 可复现命令与记录

在项目根目录执行：

```powershell
py -3 -B scripts/run_stage3.py
py -3 -B scripts/run_stage2.py --quick
py -3 -B scripts/run_stage1.py --quick
py -3 -B scripts/check_rtl_style.py
```

工具为项目本地 Icarus Verilog 13.0；编译使用 `-g2001 -Wall`，运行由 Verilog 显式 PASS/FAIL 与进程状态共同判定。日常运行不联网、不修改系统 PATH。`build/stage3/` 保存工具版本、逐项编译/仿真日志、`results.json` 和源文件 SHA256；状态先置 RUNNING，成功置 PASS，失败置 FAIL。

第三阶段 `--quick` 只将每组集成测试的随机段由 30,000 周期缩至 2,000 周期。RR、全容量 FREE、FIFO、epoch 查询穷举、故障与配置拒绝测试仍执行。随机段周期数不是已接受操作数。

## 3. 组件结果

| Testbench | 配置 | 结果 |
| :--- | :--- | :--- |
| `tb_wfq_admission_ctrl` | FAST5 | 12,513 次检查；前 1,000 个双请求持续合格周期接受 200 次，插入/出队交替，各 100 次 |
| `tb_wfq_free_slot_stack` | PTR=4、DEPTH=16 | 150 次检查 |
| 同上 | PTR=10、DEPTH=1024 | 9,222 次检查 |
| 同上 | PTR=11、DEPTH=1024 | 9,222 次检查 |
| 同上 | PTR=16、DEPTH=65536 | 589,830 次检查 |
| `tb_wfq_response_fifo` | FLOW_ID_WIDTH=8/9/12，三组 | 每组 106,983 次检查、251 次同沿生产/消费、4,550 次非法信用请求被拒绝 |

FREE 测试在每种容量下分配全部槽位、提交全部插入，再释放全部槽位，检查每个指针和最终全部 RAM 内容；最大配置验证的是 FREE 组件，未对 65,536 槽完整引擎做流量验证。默认最后分配地址为 0，满容量计数为 1024。对空栈读和满栈写的错误请求，验证 code=5 且访问关闭，不能将计数 1024 截断成地址 0。

FIFO 使用独立软件式队列检查顺序和数据，主动包含没有预留的生产、信用已满时仍请求预留、同沿消费等组合。这些非法请求用于检查组件保护，不是正常顶层流量。update_allow=0 时阻止预留/生产，已有响应仍可消费；复位清除响应和预留。

## 4. 资源集成与五拍发射

`tb_wfq_resource_ctrl` 实例化真实 `wfq_init_ctrl` 和完整资源控制 RTL。testbench 使用 live 槽位、未截断逻辑 epoch、tag、插入序号和独立 FREE/响应模型；按绝对接受周期计算 E4/E1 提交时刻，不读取 DUT phase 来决定正常提交。

testbench 提供后续 list manager 应交付的旧头指针、完整 payload 和提交请求。其稳定排序模型用于生成这些输入，**不表示本阶段已经实现或验证 RTL 链表排序**。

| PTR/DEPTH/FLOW | 随机种子 | 接受=提交 | 已消费响应 | 恰好间隔 5 拍的相邻接受 | RR 冲突 | 检查次数 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 4/16/8 | 12345 | 5,682 | 2,841 | 5,496 | 239 | 696,527 |
| 10/1024/9 | 12345 | 7,698 | 3,849 | 7,512 | 239 | 908,207 |
| 10/1024/9 | 5381 | 7,842 | 3,921 | 7,659 | 240 | 906,252 |
| 11/1024/12 | 67891 | 7,808 | 3,904 | 7,629 | 245 | 907,672 |

四组总计 29,030 次接受/提交、14,515 个响应。随机段采用请求间隙、保持至握手的插入字段、两代与超窗请求、每段 23 周期的随机响应 ready 状态；测试结束排空已接受事务、队列和响应，并验证 FREE 是全部物理地址的无重复集合。

每个采样沿检查以下内容：

- 参考资格和 RR 结果与两路 ready 一致；每沿最多一个接受，任意相邻接受至少相隔五拍。
- 插入 E1 的 FREE 返回与接受 context 对齐；插入 E4、出队 E1 提交，提交前容量和 bank 状态不提前变化。
- `free_count+alloc_reserved+queue_level==MEM_DEPTH`，两个 bank 的计数总和等于已提交队列。
- 响应 count/reserved、valid、完整 payload 和消费顺序；响应消费不改变队列和 FREE。
- empty/full 采用不同口径，满队列不能预支出队地址，响应信用不能预支当沿消费。

定向序列覆盖两代交错、65535/0 共存、第三代请求随旧代排空而解禁、空队列重建、满容量同代分配/排空、连续双请求 RR、旧响应等待期间的资源重用。驻留 65535/0 窗口时，每组组合扫描全部 65,536 个 epoch 查询编码，只有 65535 和 0 合法；这是一个窗口状态下的查询穷举，不是全部 bank 状态穷举。

默认种子 12345 观察到 8,291 个 epoch 背压周期、2,945 个可发射但响应信用不足的周期，以及 185 次超过五拍的接受间隔。无合格请求导致的间隔合法；恢复资格后按当时状态发射，不量化到固定五拍槽。两路持续合格的组件与集成段均验证五拍聚合接受，RR 连续交替对应各路十拍一次。

## 5. 沿前故障与原子性

`tb_wfq_resource_faults` 每个场景都真实初始化 FREE，先建立一个 live 节点和一个未消费响应，再对实际寄存状态、RAM 字或返回有效位注错。注入后保存全部 FREE RAM 和容量、bank、响应、RR/冷却状态，检查故障采样沿与后续沿均无部分更新。

| 配置 | 故障场景 | halt/复位场景 |
| :--- | ---: | ---: |
| PTR=10、DEPTH=1024 | 18 | 6 |
| PTR=5、DEPTH=16 | 20 | 6 |

共计 38 个跨配置故障场景、12 个停止/复位场景；同一错误在不同配置下运行，不能解释为 38 种独立错误类型。较宽指针配置额外验证 FREE 有效字与释放指针越界的 code=7；默认 10/1024 无此类越界二进制编码。

覆盖包含容量/预留损坏、bank epoch/valid 矛盾、响应信用损坏、错误/缺失/过早提交、context 不可用或不匹配、执行路径不可用、FREE read_valid 缺失、提交/payload epoch 错误，以及多错误同沿和外部事件优先级。缺失有效返回不使用任意 RAM data 推断指针故障。

错误在采样沿前撤销 cycle_allow、ready、commit_fire、FREE 读写、epoch 提交、响应预留/入队。随后锁存首次最小非零编码；后来的较小错误不覆盖首次编码。每个故障场景都验证原有响应完整保留且仍可消费，消费不会再次释放节点。

插入 E1/E2/E3/E4 各测试一次 halt，另测试插入在途和出队已预留期间复位。halt 抑制剩余修改并允许旧响应消费；它不是正常暂停/恢复接口。复位取消内容和预留并重新完整初始化。此前接受的分配预留在 fault 后可保留到复位，不尝试通过回滚继续服务。

## 6. 配置拒绝、回归和边界

以下六项均在展开阶段拒绝：

| 参数 | 原因 |
| :--- | :--- |
| ISSUE_INTERVAL=4 | 不符合当前固定排程 |
| ISSUE_INTERVAL=6 | 规格允许 PIPE6，但当前阶段只实现用户指定 FAST5；尚未支持 |
| PTR_WIDTH=9、MEM_DEPTH=1024 | 指针不足以覆盖全部节点地址 |
| PTR_WIDTH=10、MEM_DEPTH=1000 | 深度不是支持范围内的 2 的幂 |
| FLOW_ID_WIDTH=7 或 13 | 超出规格 8～12 范围 |

此前基础 RTL 未改动。第一阶段快速回归通过 13 项仿真及 8 项配置拒绝；第二阶段快速回归通过 9 项仿真及 4 项配置拒绝。本轮没有重跑第一阶段 Matcher 穷举和第二阶段双 bank 全 tag 扫描，历史完整结果保留在对应报告中。当前机械风格检查覆盖 16 个 RTL 模块及 2 个 include。

尚待第四阶段实现 DATA/NEXT、head/cache、bank 链表边界、提交描述符、pending 旁路、两个执行/写回上下文和完整顶层，并联合验证真实元数据与资源同沿原子提交。第三阶段的一项未提交资源记录不能代替两个执行/写回上下文，不能作为 busy；插入 E5 修补/E6 写回完成仍属于外部上下文生命周期。

本报告不替代 F01–F34 的完整顶层验收、每配置至少十种子且每种子十万次接受的最终随机要求、宏综合映射或 STA。没有综合面积、实际频率、时序收敛或完整引擎吞吐结论。阶段 4 的具体接线和错误门控约定见 `RTL_Implementation_Plan.md` §7.2。
