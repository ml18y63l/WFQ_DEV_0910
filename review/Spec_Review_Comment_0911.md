## 1. 评审范围

覆盖 Design_Spec_V1.md 全部 16 节及附录 A～C，重点：

1. 参数与存储组织（§2、§6）的算术一致性与参数化完备性。

4. 固定时序与端口预算（§10）的可实现性，含相邻事务四组合的逐沿重放。
5. 原子提交/overlay/并发冲突（§11）的一致性论证。
6. 初始化、复位、fault（§12、§13）的可验证性。

## 3. 重要发现（建议 RTL 启动前处理）

### I-1 初始化逐沿时序需无歧义化

**位置**：§12.2、§12.3；关联 F01（"初始化周期准确"）与断言 4/13 的采样沿。

**问题**：现文本"最后一次初始化写后留一个 guard 边沿，设置 …… `init_done=1`。下一上升沿才允许第一次请求握手"存在两种实现读法：(a) `init_done` 在 guard 沿（R_8192）作为寄存器置位，其在 R_8193 采样时可见，首握手在 R_8193；(b) guard 周期内组合给出 `init_done`，首握手提前到 R_8192。"按 8193 个时钟预算"的计数起点（R0 起、含/不含首写沿）亦未闭环。F01 要求精确核对初始化周期数，两种读法相差 1 拍，验收时会产生争议。

**建议**：在 §12.2 增加一张逐沿定义表，固定：R_0 = 首个初始化写沿；R_8191 = 末写沿；R_8192 = guard 沿（该沿将 `init_done` 等状态寄存置位）；R_8193 = 首个允许握手沿。并注明 `init_done` 为寄存输出、组合路径不得前馈到 ready 生成。

### I-2 F24 故障注入机制未定义

**位置**：§14.3 F24（"故障注入 TT.valid/RC/头缓存矛盾"）、§13.2。

**问题**：fault_code 1～6 的触发条件多数是内部状态被破坏后的检测（如"出队读到 RC=0"、"TT.valid=0"）。正常接口流量在合法工作区间内**无法到达**这些状态（§13.2 也说明 fault 不是流量控制机制），因此 F24 必须依赖对内部存储/寄存器的注入手段，但规格未定义：是 RTL 内建注错钩子、testbench 层次引用 force、后门读写（backdoor load），还是 bind checker 内翻转。不同手段对 RTL 代码（是否允许保留 syn-translate_off 的注错端口）和验证环境的要求完全不同。

**建议**：在 §14 增加一小节"故障注入实现约定"，明确：注入点清单（RC/TT/头缓存/计数器）、注入手段（建议后门 API 或层次 force，禁止综合 RTL 内留永久性注错逻辑）、注入后 DUT 期望行为（fault_code 编号、禁止部分提交、响应 FIFO 保留）、恢复路径（复位后 init_done 重新拉高）。

### I-3 DFT / MBIST 范围未声明

**位置**：§12（复位/初始化）、§6.3（RAM wrapper 契约）、§1.2（模块边界）。

**问题**：规格已声明不包含 ECC（§6.2），但未提及 MBIST/扫描链/repair 对 ASIC 路径的处理。默认配置含 8 类 RAM 宏、约 60 KiB 存储位（其中 TT/RC 各 8192×13 为大块）；若 ASIC 流程要求 MBIST，`wfq_sync_ram_1r1w` 的端口契约需要在初始化接管之外**再预留 BIST 模式的端口仲裁**（或明确声明由宏级/顶层 BIST 控制器接管、wrapper 不感知）。该决定影响第一批就要编写的 wrapper RTL，事后补入会牵动所有 RAM 实例。

**建议**：在 §12 或 §1.2 增加 scope 声明，二选一：(a) V1 为验证/FPGA 评估基线，DFT/MBIST 为非目标，wrapper 不预留端口，ASIC 化时另行版本；(b) wrapper 预留 `bist_mode` 端口旁路，初始化控制器与 BIST 控制器经统一仲裁。若选 (b) 需同步修订 §5.2 模块职责表。

## 4. 一般建议

### G-1 增加 `exact ↔ RC>0` 等价断言

§7.2 的 matcher `exact`（LE 模式选中 query 本身）按 §7.1 不变量 `L3[..][c] == (RC != 0)` 恰好等价于 `RC[bank,tag] > 0`（重复键场景）。插入流水线在 E0 已读 RC、E3 得到 exact，两者跨通路独立，是廉价且高价值的交叉检查点。建议在 §14.5 增加断言："插入事务中 `exact==1` 当且仅当该事务读到的旧 RC > 0"，可在早期暴露 Trie 与 RC 失配类缺陷（对应附录 B 第 3、4 条错误模式）。

### G-2 出队 E1 级联清除的化简与并行性提示

§7.6 出队清除按新值判断（`new_leaf==0` 才动父、`new_parent==0` 才动根）。由于被清位在旧值中必为 1，可等价化简为：

~~~text
WE_L3 = last_of_key                                // RC 1→0
WE_L2 = WE_L3 && (old_leaf  == 16'h1 << c)
WE_L1 = WE_L2 && (old_parent == 16'h1 << b)
~~~

即"是否级联到下一层"仅是两个 16-bit 等值比较（本次评审已用 20,000 次随机操作模型验证该化简与按新值判断完全等价，L1/L2/L3 与 RC 全量重建一致）。三个写口的 WE 生成链最深为"等值比较 → AND → 等值比较"，写数据（`old & ~(1<<x)`）互相独立。建议把该化简与"E1 各写口使能生成必须并行、不得串行穿过多级零检测"写入 §9.4 或 §15.2，直接服务 §10.3 声明的首要 STA 路径。

### G-3 RAM 宽度的参数化公式

§2.1 允许 `PTR_WIDTH = 4~16`、`FLOW_ID_WIDTH = 8~12`，§14.4 要求小容量配置验证，但 §6.1 表中的宽度均为默认值数字（13/37/12）。建议在 §6.1 补一行通用公式：`TT/RC 宽 = 1 + PTR_WIDTH`、`NEXT 宽 = 1 + PTR_WIDTH`、`DATA 宽 = EPOCH_WIDTH + TAG_WIDTH + FLOW_ID_WIDTH`、`FREE 宽 = PTR_WIDTH`、`L1/L2/L3 深 = EPOCH_BANKS × 16^level`，避免小容量跑配置时手工换算出错。

### G-4 `ready` 依赖 `valid` 的集成声明

§4.2 明确允许 `ready` 依赖两端 `valid`、仲裁与资源条件。这在本模块点对点集成下成立，但与常见互联规范（ready 不依赖 valid 的风格）不同，且引入 `insert_val → insert_ready` 组合路径。建议在 §4.2 补一句"此为有意选择；若上游经寄存 slice / AXI-Stream 类互联接入，skid buffer 由集成方负责"，避免联调阶段的接口归责争议。

### G-5 全排空后 `base_epoch` 的残留语义

§3.3.5 规定空队列后首条插入可任意 epoch 并重建 base，但未说明全排空瞬间（两 bank 同时无效）`base_epoch` 寄存器的值应如何处理。行为上它是 don't-care（重建时覆盖），但 RTL 作者与验证断言（断言 11："两个活跃 bank 的完整 epoch 必须为 base 与 base+1"）需要一个明确前提：该断言仅在 `queue_level>0` 时适用。建议补一句："队列完全为空时 `base_epoch` 不定义语义，断言 11 以非空为前提。"

### G-6 上游协议违规鲁棒性显式列为非目标

§13.3 要求验证环境断言上游保持 valid/payload 等协议行为，但未说明 DUT 对违规输入（背压期间撤销 valid 等）的行为是否纳入测试。按 §1.2/§13 的定位应不测。建议在 §13.3 或 §14.4 明确："本模块不保证对上游握手协议违规的鲁棒性，验证计划不包含此类负向激励"，防止验证计划评审时被要求补充无定义行为的用例。

### G-7 验证载体与工具链基线

§14 要求参考模型、bind 检查、SVA 断言、随机回归，§14.6 要求 lint/elaboration 检查，但未指定：RTL 语言版本（建议 SystemVerilog-2012 及以上）、验证载体（纯 SV testbench + 程序块 / UVM / Python 协同仿真）、lint 工具、仿真器。断言 1～13 的写法（尤其采样沿与 NBA 可见性，§14.5 已提醒）和 I-2 的注入手段都依赖该基线。建议在 §14.1 开头补一个"环境基线"小表。

## 7. 本次独立复算通过项

以下内容在本次评审中经独立推导或脚本复算验证一致（脚本与附录 C 模型相互独立）：

1. **存储占用算术**（§6.2）：Trie 25,632 + TT 106,496 + RC 106,496 + DATA 151,552 + NEXT 53,248 + FREE 49,152 = 492,576 bit ≈ 60.13 KiB。✓
2. **Select & Look-Ahead 4×4 公式**（§7.3）：按给出的 G/S/local_onehot 公式实现，对全部 65,536 个 bitmap 验证 onehot 恒等于"最大置位位"。✓
3. **A/B/C 前驱候选类的完备性与优先级**（§7.4）：51 个集合（含空集、{0}、{4095}、全集、单根分支密集、跨段稀疏、随机）× 全部 4,096 个 query，共 208,896 次，与暴力 `max{y≤x}` 零失配；三类的划分确为对 `y≤x` 字典序空间的不重不漏分割。✓
4. **定向用例期望值**：F07（C 类 → 0x1FF）、F08（B 类 → 0x210）、F09（A 类 → 0x245）。✓
5. **marker 精确清除级联**（§7.6）：20,000 次随机插入/出队（含热点键、极值键）后，L1/L2/L3 与按 RC 全量重建的期望位图完全一致；同时验证 G-2 的 `==onehot` 化简等价。✓
6. **吞吐表与初始化预算算术**（§10.6、§12.2）：四档频率的 f/8、f/16 换算；8,193 周期 @250 MHz = 32.772 μs、@150 MHz = 54.620 μs。✓
7. **8 拍重叠端口排程逐沿重放**（§10.4、§10.5）：Insert/Insert、Insert/Extract、Extract/Insert、Extract/Extract 四种相邻组合下，每个物理 RAM 副本每沿均不超 1R1W；唯一的同沿同址冲突（T0 插入 E8 写 `NEXT[p]` 与 T1 出队 E0 读 `NEXT[p]`，发生于 T0 插入在"第二节点之后"的场景）由 §6.3"本沿新提交写集合优先"的旁路规则覆盖；其余跨事务读均晚于前事务的物理写沿。✓
8. **跨 bank 边界正确性推演**：旧代最大 tag 的重复插入（前驱 = `bank_tail[old]`，后继 = 新代头）、新代最小 tag 插入、旧代末节点出队推进 base、epoch 65535→0 回绕——链表结构均自然给出正确序（TT 尾是真实链表节点，其 NEXT 天然跨越 bank 边界）。✓
9. **资源不变量**：`free_count + alloc_reserved + queue_level == MEM_DEPTH` 在 E0 接受 / E1 出队提交 / E7 插入提交各事件沿后保持。✓
10. **与草稿的一致性**：Initial_Design_Spec.md 与 V1 的全部实质差异（epoch、13-bit RC、时延口径、接口握手、NULL 表示等）均已由 §1.4 修正表声明，未发现未声明的冲突。✓

## 8. 对验证计划的补充建议

1. **F04 补排空段**：F04 只验证到满容量驻留（RC=4096 不回绕）。建议增加 F04b：填满 4096 后全部出队（可交错响应背压），校验出队序、终态 `empty/full/queue_level/free_count` 与地址全回收，覆盖"满→空"全程。
2. **真正同址 RAW 的单元级用例编号**：§14.3 对 F22 的注记已指出顶层合法流量可能无法构造特定同址组合，但未在 §14.2 落一个对应单元用例。建议在 §14.2 RAM wrapper 行明确增加："U-RAM：T0 写 addr A 与 T1 读 addr A 同沿发出（分别模拟 E8 写回与 E0 读），验证旁路返回新值；以及 A 不同址时返回 RAM q"。
3. **epoch 跳变与 bank 复用的随机权重**：F15 只覆盖一次 65535→0。建议 §14.4 随机流量的 epoch 生成器显式包含"跳变至 65535 邻域"与"驱动 bank 复用 ≥3 次"的定向权重，否则两次独立回归间该路径的覆盖命中数不稳定。
4. **状态输出一致性断言**：`queue_level` 在插入已接受未提交期间不变、`empty` 期间保持 1（§4.5），建议列为独立断言，防止实现把 `empty` 接到组合比较上。

## 9. 评审结论

Design_Spec_V1.md 在排序语义、epoch 窗口协议、固定时延流水、端口预算与并发一致性方面内部自洽，核心算法经独立复算正确，未发现需要在 RTL 中"边写边猜"的功能空白（§16.3 亦如实界定了边界）。
